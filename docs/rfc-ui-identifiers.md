# RFC: Идентификаторы UI-узлов и восстановление после обновления

## Контекст, проблема и объем

`control_<uuid>` из канонического `UiSnapshot` безопасен как непрозрачная цель действия, но UUID, созданный в памяти браузера, исчезает при reload, navigation и новом DOM. LLM, backend и журнал действий не могут считать такой идентификатор долговременной ссылкой.

RFC определяет два разных класса идентификаторов: action-id для исполнения действия в текущем снимке и semantic-id для сопоставления узла между снимками. Он охватывает сохранение и повторное разрешение ссылок после обновления страницы. Он не определяет формат передачи снимка в LLM и не заменяет продуктовые бизнес-ключи.

## Цель

- Не допускать выполнения действия по устаревшему или неоднозначному идентификатору.
- Сопоставлять один и тот же видимый контрол между соседними снимками, reload и navigation, когда DOM предоставляет достаточные стабильные признаки.
- Делать степень уверенности и причину сопоставления наблюдаемыми.
- Использовать product-owned идентификаторы, когда они есть, и не превращать DOM-путь в ложную гарантию стабильности.

## Детальный дизайн

### Две области идентичности

Каждый интерактивный узел получает `actionId`, равный существующему `UiNode.id`, и живущий только в рамках `snapshotId`. В LLM action передаются `{ snapshotId, rootId, controlId, toolId }`; executor принимает действие только при совпадении актуального снимка и allow-list tool.

Для наблюдения между снимками parser дополнительно вычисляет `semanticId` и не отправляет его в LLM по умолчанию. Он является детерминированным хешем нормализованного набора стабильных признаков:

```ts
interface UiIdentity {
  actionId: string;
  semanticId?: string;
  identitySource: "product-key" | "aria" | "structural" | "ephemeral";
  confidence: "high" | "medium" | "low";
}
```

Состав хеша включает версию алгоритма, `root`-namespace, тип контрола, `data-testid`/`data-e2e`/продуктовый key, `name`, `formcontrolname`, стабильный `id`, semantic role и доступное имя. Значения нормализуются: trim, Unicode normalization, collapse whitespace, без секретных и пользовательских значений. Hash кодируется как `ui_<algorithmVersion>_<base64url>`.

### Приоритет источников

| Приоритет | Источник | Устойчивость | Правило |
| ---: | --- | --- | --- |
| 1 | Продуктовый `data-testid`, `data-e2e`, бизнес-ключ | Высокая | Использовать как основной semantic-id при уникальности в root. |
| 2 | `id`, `name`, `formcontrolname` | Средняя | Использовать вместе с типом/ролью, не как глобальный ключ. |
| 3 | ARIA role и доступное имя | Средняя | Дополнять контекстом semantic group; одинаковые label требуют disambiguator. |
| 4 | XPath/CSS path, sibling index | Низкая | Хранить только как диагностический locator и fallback внутри одного DOM. |
| 5 | Runtime UUID | Эфемерная | Только action-id; не использовать для восстановления. |

XPath хранится в `__xpath` и никогда не является semantic-id. Индекс sibling допустим лишь в structural fallback, маркируется `low` confidence и не может автоматически исполнять отложенное действие.

### Разрешение после обновления

При reload клиент сохраняет только ссылку `{ semanticId, rootHint, controlType, labelHint, algorithmVersion }`, а не `actionId`. После нового snapshot resolver ищет кандидатов в следующем порядке: точное совпадение product-key, точный `semanticId`, затем ограниченное сравнение стабильных атрибутов в `rootHint`.

Resolver возвращает один из результатов:

```ts
type ResolveResult =
  | { status: "resolved"; actionId: string; confidence: "high" | "medium" }
  | { status: "ambiguous"; candidates: Array<{ actionId: string; semanticId?: string }> }
  | { status: "not-found" }
  | { status: "stale"; reason: "algorithm-version" | "root-changed" | "low-confidence" };
```

Автоматически продолжать workflow разрешено только для `resolved` с `high` confidence. При `medium` требуется повторное подтверждение модели по актуальному LLM-контексту. `ambiguous`, `not-found` и `stale` прекращают действие и записываются в telemetry.

### Коллизии, приватность и наблюдаемость

Уникальность `semanticId` проверяется в пределах root. При коллизии добавляется детерминированный disambiguator из семантической группы и stable product context; если уникальность не достигнута, `semanticId` не выдаётся. В backend логируются algorithm version, source, confidence, collision count, resolve status и latency. Сырые значения полей, label с PII, XPath и DOM не логируются без redaction policy.

### Внедрение

1. В shadow mode рассчитывать `semanticId` и измерять collision/resolution rate без изменения dispatch.
2. Ввести обязательные product-key атрибуты для критичных действий и форм.
3. Разрешить восстановление только для `high` confidence, с telemetry причин отказа.
4. Версионировать алгоритм и мигрировать сохранённые ссылки явным re-resolution, а не изменением значения на месте.

## Недостатки

- Без продуктового ключа одинаковые кнопки и динамические списки нельзя надёжно отличить после изменения DOM.
- Стабильные label могут быть локализованы или переименованы, поэтому ARIA-based fingerprint не является вечной ссылкой.
- Product keys требуют дисциплины команд и могут случайно раскрывать бизнес-данные при неправильной политике логирования.
- Resolver добавляет состояние, метрики и правила отклонения в пользовательский workflow.

## Альтернативы

| Вариант | Причина отказа в качестве основного решения |
| --- | --- |
| Только UUID | Не переживает reload и не даёт диагностики соответствия. |
| Только XPath | Ломается при layout-обёртках, reorder и виртуализации; слишком хрупок для действий. |
| Только HTML `id` | Не все контролы имеют id, а его уникальность обычно ограничена текущим документом. |
| Глобальный UUID в DOM | Требует модификации приложения и не решает переиспользование/версионирование значения. |
| LLM выбирает похожий контрол по тексту | Недетерминированно и небезопасно при одинаковых label. |
